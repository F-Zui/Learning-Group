01 · 输入输出与评测机制

把“题目 → 代码”这条最短链路打通：知道评测机在比什么，掌握 cin/cout 的结构与用法，并第一次建立“数据范围决定变量类型”的意识。
⭐ 已学范围入门预计 45 分钟cin/coutgetline整数范围评测机制

先接受一个事实：评测机不理解你的程序，它只做一件事——把你输出的字节和标准答案的字节逐字比对。所以从第一天起，你写的每一行输出都要能回答一个问题：它会不会出现在标准答案里？

推导cin：一串字节怎么变成两个整数覆盖：cin / 链式读入 / 跳过空白 / 类型匹配需求 → 尝试 → 验证 → 定理
问题

题目说“输入两个整数”，可评测机送进来的只是几个字节：2、空格、3、换行。程序里并没有“读一个整数”这种天生动作——得有人替我们决定：从哪里开始取、到哪里停、怎么把字符变成数。

1先看清输入的真实形状

把输入当成一条字节流：空白字符（空格、Tab、换行）只起分隔作用，本身不是数据。2 3 加换行，真正的内容只有 '2' 和 '3' 两个字符，夹着两个分隔符。

于是“读两个数”可以拆成三步：跳过前导空白 → 取一段连续的非空白 → 按目标类型把这段解析成数。

验证 / 关键

数一遍字节：'2'、空格、'3'、换行，共 4 个。两次读入各取走 1 个，两个分隔符都不进变量——这就是“数据分几行写也对”的原因。

2把这套动作打包成一个流对象

C++ 把“字节流 + 当前位置 + 是否出错”打包成 std::cin，再用提取运算符 >> 表示“取下一个词”。

签名
std::cin >> 变量1 >> 变量2 >> ...;
组成含义 / 格式要求
std::cin标准输入流对象，代表“键盘/文件”。程序中只有一个，直接拿来用。
>>提取运算符：把输入里的下一个“词”取出来，放进右边变量。
链式写法cin >> a >> b 等价于 (cin>>a)>>b，读第一个数给 a，读第二个给 b。
跳过空白自动跳过空格、Tab、换行，所以数据分行写也能正确读入。
类型自动匹配给 int 读整数，给 double 读小数，给 char 读一个非空白字符。
验证 / 关键

>> 左结合，所以 cin >> a >> b 先读 a 再读 b，顺序不会乱；而每次读到的“词”长什么样，由右边变量的类型决定。

3验证：它什么时候会失败

提取运算符返回的就是 cin 本身，所以既能链式写，也能放进 while 的条件里。但它不是万能的：类型对不上、数据不够，都会让它进入失败状态。

最小可运行示例
#include <iostream>          // cin / cout 都在这个头文件
using namespace std;     // 展开 std 命名空间，之后可以直接写 cin

int main() {
    int a, b;
    cin >> a >> b;       // 一次读两个整数
    cout << a + b;
    return 0;
}
失败现场
int a = 0, b = 0;
cin >> a;               // 输入 "abc"：解析失败，cin 进入失败状态
cin >> b;               // 此后每个 >> 都不再生效，b 保持 0
验证 / 关键

换成只给一个数 2，第二次 >> 同样失败，b 保持原值；局部变量没初始化时这个“原值”是随机的，所以要先想清楚数据够不够。

于是我们得到：

cin 是一台“按空白切词、按变量类型解析”的机器，链式 >> 把多个词依次送进多个变量。

两条必须记住的边界

读入类型必须和变量类型一致：给 int 变量输入“abc”，cin 会失败并让后续读入全部失效。

cin 不会检查你有没有读够。数据比预期少时，后面的变量保持原值（局部变量是随机值）。

追问 · 把这一步想透
  1. 如果输入是“10 个数，每行一个”，用 cin >> x 循环 10 次能正确读入吗？为什么？
    想好了？点开核对思路与解析
    能正确读入。cin 的提取运算符会自动跳过空格、Tab 和换行，所以“每行一个数”和“一行十个数”对它没有区别，循环 10 次就按顺序拿到 10 个值。要注意每个数必须真的读进一个变量（int x; cin >> x;），读进同一个 x 十次只会留下最后一个。
    常见错路是以为“按行给的数据就必须按行读”，改用 getline 再 stoi，结果忘了处理残留换行，第一次 getline 读到空串，后面全部错位。
推导cout：把内存里的数变成屏幕上的字节覆盖：cout / 链式输出 / 换行与 endl / fixed + setprecision需求 → 尝试 → 验证 → 定理
问题

算出来的 a + b 在内存里是 32 位二进制，而评测机只看得到字节。中间必须有人做转换：把二进制拆成十进制字符，再一个字节一个字节送出去。更麻烦的是——多一个空格、少一个换行，都算答案的一部分。

1先明确要输出什么

输出的最小单位是字节，不是“数”。5 是一个字节，ans = 5 是八个字节，两者在评测机眼里完全不同。

所以输出这一步要回答三件事：输出哪些内容、内容之间插什么、最后要不要换行。

验证 / 关键

A+B 的答案只有 '5' 加一个换行，共 2 个字节；写成 "ans = 5" 就是 9 个字节，多出来的 7 个字节全部判错。

2用插入运算符把内容串起来

std::cout 是标准输出流，<< 表示“把右边的内容转成字符，送进流”。它同样可以链式写，混着送字符串和数字。

签名
std::cout << 内容1 << 内容2 << ...;
组成含义 / 格式要求
std::cout标准输出流对象，代表“屏幕/文件”。
<<插入运算符：把右边的内容转成字符，送进输出流。
'\n'换行符，一个字符，不刷新缓冲区，速度最快。
endl换行 + 立刻刷新缓冲区。循环里大量用会慢 3~10 倍。
格式控制cout << fixed << setprecision(2) 固定两位小数，需要 #include <iomanip>。
验证 / 关键

'\n' 是字符常量、endl 是操纵器：前者只往缓冲区塞一个字节，后者还会把缓冲区真的交给操作系统——快慢差别全在“刷不刷新”这一步。

3验证：输出格式就是答案格式

把三种常见写法放到一起对比，一眼就能看出字节差在哪。

示例
cout << a << " " << b << "\n";     // 输出 a、空格、b、换行
cout << "ans = " << ans << "\n";    // 文字和数字可以混着插
cout << fixed << setprecision(3) << 1.0 / 3;   // 0.333
验证 / 关键

cout 不需要写格式符（不像 printf 要 %d、%lf），类型对就行；但“类型对”只保证能被打印，不保证打印出来的字节是题目要的。

于是我们得到：

cout 负责把值翻译成字节，格式由你插进去的每一个字符决定。

注意

cout 不需要写格式符（不像 printf 要 %d、%lf），类型对就行。

循环十万次以上时，用 '\n' 而不是 endl。

追问 · 把这一步想透
  1. 如果题目要求“先输出 a，再输出 b，中间用逗号分隔、行末不要空格”，cout 那句该怎么写？试着只改一行。
    想好了？点开核对思路与解析
    只改最后一行：cout << a << ',' << b << '\n';。逗号是一个字符，直接插进流里，前后都不加空格；行末要求“不要空格”，所以最后插进去的必须是换行符而不是空格。写完数一遍这一行输出的字节：数字、逗号、数字、换行，多一个空格就是 WA。
    常见错路是只把原来两个数之间的 ' ' 换成 ' , '，逗号两边各带一个空格，逐字节比对直接把答案判错。
  2. 把 int 换成 double 读入 1 2，输出会变成什么样？为什么会多出小数？
    想好了？点开核对思路与解析
    直接 cout << a + b 输出仍然是 3，并不会多出小数——cout 默认按 6 位有效数字打印 double，整数后面没有非零位就不补小数点。会“多出小数”的是格式控制：to_string(3.0) 得 3.000000，fixed << setprecision(6) 或 printf 的 %f 也是 3.000000。所以真正的坑是：标准答案写 3，你交了 3.000000，逐字节比对就是 WA；顺带记住 double 只能精确表示 2⁵³ 以内的整数，再大就不保证逐位精确了。
    常见错路是以为“double 天生带小数点”，于是把整数答案全换成 double 输出。
推导大数据为什么读得慢：同步与绑定覆盖：ios::sync_with_stdio(false) / cin.tie(nullptr) / 放置位置需求 → 尝试 → 验证 → 定理
问题

第 1 节的程序读两个数只要几微秒。可当 n = 106 时，同样的 cin 会慢到 TLE——不是循环写得差，而是 cin 每读一次都在做两件额外的事。

1看清楚慢在哪

第一件：默认情况下，C++ 的 cin/cout 与 C 的 scanf/printf 共享同一套缓冲区，每次读写都要先“对表”。第二件：cin 和 cout 默认绑定，每次 cin 之前会先把 cout 的缓冲区刷掉。

这两件事都是为了保证“混用两套流时顺序正确”，代价是一读一刷。数据量大时，刷新的次数就是 TLE 的来源。

验证 / 关键

106 次读入 = 106 次多余检查；如果中途还穿插输出，再叠加 106 次刷新，常数直接翻几倍。

2关掉它们：两行咒语

C++ 把这两个开关暴露成两个成员函数，各调一次即可。

签名
ios::sync_with_stdio(false);
cin.tie(nullptr);
组成含义 / 格式要求
sync_with_stdio(false)关闭 C 流（scanf/printf）与 C++ 流（cin/cout）的同步。关掉后 cin 快 3~5 倍。副作用：此后不能再混用 scanf 和 cin。
cin.tie(nullptr)解除 cin 对 cout 的绑定。默认每次 cin 前会先刷新 cout，解除后少一次刷新，更快。
放在哪必须写在 main 开头、任何输入输出之前，写一次就够。
验证 / 关键

两行都是“全局开关”，写在第一次 cin 之后就没用了；也只影响速度，不影响结果。

3验证：什么时候值得写

它们不是必需的，读入量小时看不出差别；但写一次的成本为零，所以竞赛模板里人手一份。

示例
int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n; cin >> n;              // 读 10^6 个数也不会慢
    for (int i = 0; i < n; ++i) { int x; cin >> x; }
    return 0;
}
验证 / 关键

关同步后如果又写了 scanf，两套缓冲区各自为政，读入顺序可能错乱——这是“提速”唯一真正的副作用。

于是我们得到：

读入慢不是 cin 的锅，是它在替你做兼容；关掉兼容就快。

注意

只有输入量很大（≥ 10⁵ 个数）时才明显有用，但养成习惯没坏处。

关同步后不要再用 scanf/printf，否则读写顺序会乱。

追问 · 把这一步想透
  1. 为什么 endl 会比 "\n" 慢？慢在哪一步？
    想好了？点开核对思路与解析
    endl 等于先输出一个 '\n'，再调一次 flush。慢就慢在 flush：它把缓冲区里攒着的字节真的交给操作系统（评测时是一次 write 系统调用），循环 10⁶ 次就是 10⁶ 次系统调用；而 '\n' 只是往缓冲区塞一个字节，缓冲区满了（通常 4KB~64KB）才自动刷一次，系统调用少三个数量级，正文给的差距是 3~10 倍。
    常见错路是以为“endl 只比 \n 多一点点开销”，差别全在那个 flush 上，不在换行上。
推导getline：当数据里本身就有空格覆盖：getline / 整行读入 / 与 cin 混用的残留换行需求 → 尝试 → 验证 → 定理
问题

cin >> 的规则是“按空白切词”，可题目要求读的偏偏是一整行带空格的文字。用 cin >> s，你只会拿到第一个词，后面的内容还留在缓冲区里。

1先确认 cin >> 停在哪

cin >> s 读到空白就停，并且不把那个空白取走。所以 hello world 只会进来 hello，空格和 world 仍在缓冲区。

要读整行，就需要一个“读到行尾、并把行尾换行符也处理掉”的函数。

验证 / 关键

这解释了两件事：为什么 cin >> s 之后 s.size() 永远等于词长；以及为什么下一次读入会先撞上那个没被取走的空格。

2换成 getline：一次取一行

std::getline 从流里一直读到 '\n'，把换行符取走丢掉，剩下的整行内容存进 string。

签名
std::getline(std::cin, s);
组成含义 / 格式要求
std::cin从哪个流读。
sstring 变量，读到的整行内容存这里（不含结尾的换行符）。
读到哪里停读到 '\n' 为止，并且把 '\n' 从流里取走丢掉。
常见搭配当输入含空格时必须用它；cin >> 只会读到一个“词”。
验证 / 关键

返回值也是流本身，所以可以写 while (getline(cin, s)) 一直读到文件尾。

3验证：混用时的残留换行

最典型的坑：先用 cin >> n 读一个整数，紧接着 getline。整数读完后，那一行的换行符还留在缓冲区，getline 立刻读到它，得到一个空串。

示例
string line;
getline(cin, line);              // "hello world" 整行读进来

int n; cin >> n;
cin.ignore();                    // ★ 先吃掉 n 后面残留的换行
getline(cin, line);              // 否则这里读到的是空串
验证 / 关键

cin.ignore() 不多不少吃掉一个字符，正好是那个残留的 '\n'。漏掉它的症状非常固定：读到空串，后面所有数据全部错位。

于是我们得到：

按“词”读用 cin >>，按“行”读用 getline；两者混用时先 ignore 掉残留换行。

注意

cin >> n 之后直接 getline，会读到空串——因为换行还留在缓冲区里。

解决办法：中间插一句 cin.ignore()。

算法落地A+B：把题目翻译成三段代码覆盖：洛谷 P1001 / 读入—计算—输出的最短闭环
需求

例题 · A+B Problem · 洛谷 P1001 入门

输入两个整数 a、b（|a|,|b| ≤ 10⁹），输出它们的和。

样例
输入：
2 3
输出：
5
1声明两个整数变量
第 1 段：声明
int a, b;              // ① 两个整数变量，此刻是随机值
为什么

题目给的范围是 |a|,|b| ≤ 10⁹，32 位 int 的上限约 2.14×10⁹，装得下；两个数相加最多 2×10⁹，也刚好在 int 之内。范围再大（比如 10¹⁸）就必须 long long。

2按顺序读入两个数
第 2 段：读入
cin >> a >> b;         // ② 链式读入：先 a 后 b，空格换行都被跳过
为什么

链式写法保证先读 a、再读 b；输入里是空格还是换行作分隔，对 >> 没有区别。这一步同时依赖 #include <iostream> 和 using namespace std;——前者让 cin/cout 存在，后者让你能写 cin 而不是 std::cin。

3算出结果并输出，末尾换行
第 3 段：计算并输出
cout << a + b << "\n"; // ③ 先算 a+b，再转成字符插入输出流，最后换行
为什么

只输出数字和换行：任何提示语（如“请输入两个数：”）都会被当成答案的一部分；行末多一个空格同样判 WA。多数题对行末换行不敏感，但养成加 "\n" 的习惯。

4拼成完整程序
完整代码
#include <iostream>
using namespace std;

int main() {
    int a, b;              // ① 声明：两个整数变量，初始是随机值
    cin >> a >> b;         // ② 读入：按顺序把前两个数放进 a、b
    cout << a + b << "\n"; // ③ 计算并输出，末尾换行
    return 0;
}
为什么

int main() 是程序入口，评测系统从这里开始执行；return 0; 告诉它“正常结束”，不写多数编译器也会补，但建议写。三段之外没有别的逻辑——这就是本题的全部。

竞赛用法

题型特征：题面只有“读入若干个数 → 算 → 输出”，没有分支也没有数据结构。看到这种题，先在草稿上写三段骨架，再填细节。

复杂度：读入 2 个数、一次加法、一次输出，O(1)。

常见坑：输出提示语；行末多空格；把 10¹⁸ 级的和塞进 int（本题 2×10⁹ 贴边，题目一改就翻车）。

自测：2 3 → 5、1000000000 1000000000 → 2000000000（检验 int 上限）、-5 3 → -2（检验负数）。

模型：读入-计算-输出O(1)坑：输出提示语 / 行末空格 / int 溢出
追问 · 落到代码上再想一遍
  1. 评测机是怎么比较你的输出和标准答案的？它会不会忽略多余空格？
    想好了？点开核对思路与解析
    评测机把你的输出和标准答案都当字节流，逐字节比较，它不理解“答案”，也不会替你把多余空格当成格式。所以 cout << "ans = " << x 里的 ans = 会被当成答案的一部分，行末多一个空格同样 WA；多数 OJ 只额外容忍行末换行和文件末尾的空白。
    常见错路是拿“样例看起来对”当通过标准——样例是给人看的，评测是给字节看的，两者之间没有“差不多”。
这一节最容易犯的 4 个错

输出提示语。写 cout << "请输入两个数：" 会直接 WA——因为这句话会被当成答案的一部分。

用 int 存超出范围的结果。本题 a+b 最大 2×10⁹，刚好卡在 int 上限（2.147×10⁹）附近；题目若改成 10¹⁸ 就必须用 long long。

忘记换行。多数题对行末换行不敏感，但有些题严格比对，养成加 "\n" 的习惯。

多打空格。行末多一个空格，严格评测（如 NOIP）会判 WA。

数学补给 · 为什么 int 的上限是 2.1×10⁹

int 占 4 字节 = 32 位。其中 1 位是符号位，剩下 31 位表示大小。

最大值 = 2³¹ − 1 = 2147483647 ≈ 2.14×10⁹。最小值 = −2³¹ = −2147483648。

类型字节范围十进制位数
int4±2.14×10⁹10 位
long long8±9.22×10¹⁸19 位
unsigned long long80 ~ 1.84×10¹⁹20 位

记住“19”这个数：long long 最多表示 19 位十进制整数。超过 19 位就必须用高精度（字符串/数组模拟）。

挑战题 · 小鱼的游泳时间
洛谷 P1425入门去洛谷做这题 ↗

小鱼从 a 时 b 分游到 c 时 d 分，中间没有休息。求它一共游了多少小时多少分钟。

输入一行 4 个整数 a、b、c、d（0 ≤ a,c ≤ 24，0 ≤ b,d ≤ 59），保证结束时刻晚于开始时刻。

输出一行两个整数，表示共游的小时数和分钟数。

引导性提示（先只看这里）

不要“小时减小时、分钟减分钟”，那样会遇到分钟不够减的情况。

把所有时间先统一换成“从 0 点开始算的第几分钟”，相减后再拆回小时和分钟。

拆法：总分钟 ÷ 60 得到小时，总分钟 % 60 得到分钟。

想看思路了？点开完整思路

开始时刻 = a × 60 + b（分钟）。结束时刻 = c × 60 + d。

总时长 = 结束 − 开始。

输出 总时长 / 60 和 总时长 % 60。

为什么这样一定对：分钟制是一个“统一单位”，换算后相减等价于时间差，不受进位影响。

还是不会？点开题解代码与拆解
参考代码
#include <iostream>
using namespace std;

int main() {
    int a, b, c, d;
    cin >> a >> b >> c >> d;

    int start = a * 60 + b;      // 开始时刻换算成分钟
    int end   = c * 60 + d;      // 结束时刻换算成分钟
    int span  = end - start;     // 总时长（分钟）

    cout << span / 60 << " " << span % 60 << "\n";
    return 0;
}
关键片段拆解
片段作用
a * 60 + b把“a 时 b 分”压成一个整数。这一步把二维的时间变成一维的数，后面就能直接相减。
end - start统一单位后相减一定正确，不用管分钟借位。
span / 60整数除法，向下取整，正好是完整的小时数。
span % 60余数就是不足一小时的分钟数。
<< " " <<两个数之间用一个空格隔开，行末只换行不加空格。
这题最容易错的地方
  • 图省事写成 d - b 和 c - a，遇到 “1 50 → 2 20” 这种分钟不够减的情况就错。
  • 用 %02d 输出前导零——题目没要求，输出 01 会 WA。
  • 忘了最后换行。
