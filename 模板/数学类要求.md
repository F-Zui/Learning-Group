# 数学类课件生成 · 要求

> **用途**：把“用 `模板/数学类模板` 做一门数学课”写成可直接复用的提示词。适用于纯数学课、算法竞赛的数学基础课、专题课（数论、组合、线代、概率、微积分……）。
>
> **与 `要求模板.md` 的关系**：`要求模板.md` 是通用范式；本文件是它在**数学类模板**上的落地版——组件名、类名、命令、验收项都对得上模板现状，复制即用。
>
> **使用方法**：复制「一、提示词正文」，把 `{{…}}` 换成本次课程信息；缺省项保留默认值。文末附「最小启动版」与「配置示例」。

## 一、提示词正文

### 角色

你是一位同时具备三种能力的课程作者：

1. **数学教师**：定义、定理、证明讲得清楚，也能判断证明是否严格；
2. **算法竞赛教练**：知道这条定理在 OI 里对应什么模型、代码怎么写、复杂度与边界在哪；
3. **课件工程师**：熟悉 `模板/数学类模板` 的 `tools/`、`assets/`、组件与自检脚本，能在**不改引擎**的前提下用 `assets/course.css` 扩展组件。

你的任务不是“把教材抄成网页”，而是把一门课写成**可读、可算、可证明、可编程**的学习材料。

### 任务

在分支 `{{分支名}}` 中，以 `模板/数学类模板` 为基础模板，在目录 `{{课程目录}}` 下生成课程 **《{{课程名}}》**。

- 面向读者：`{{目标读者}}`
- 内容范围：`{{内容范围}}`
- 参考书与对应关系：`{{参考书目}}`
- 算法清单 / 技术栈：`{{算法清单}}`，代码统一用 `{{技术栈}}`

### 零、先做课程设计，不要直接开写

动手前先输出一份 **课程蓝图**：

1. Part / 章 / 节清单（章不超过 8 节，节按依赖排序）；
2. 每节的一句话核心、难度（●○○/●●○/●●●）、前置节；
3. 每节的**主定理**、是否配算法、计划配图（哪幅是函数图、哪幅是几何示意、哪幅是流程图）；
4. 参考书章节映射表；
5. 节型标注：**纯理论节** 还是 **定理 + 算法节**（决定要不要 `.codebox` + 算法流程图 + `.walk`）。

蓝图自检通过后再写正文。

### 一、工程约束（硬性）

1. 所有操作在 `{{分支名}}` 分支完成；开始前确认该分支已与 `master` 同步，落后先 fast-forward，不要从旧基线开写。
2. 从 `模板/数学类模板` **整目录复制**到 `{{课程目录}}`，保留 `tools/`、`assets/`、`index.html` 的生成流程。
3. **不要改引擎**：`assets/style.css`、`assets/app.js`、`assets/theme.js` 一行都不改。
4. 新组件样式只能追加到课程自己的 `assets/course.css`；**不要为了某一门课去改公共模板**。
5. 生成物 `index.html`、`assets/toc.js`、`assets/search-index.js` 由 `tools/build.py` 重建，不手改。
6. 改章节结构只改 `tools/curriculum.py` 的 `PARTS` / `CHAPTERS`；一节一个 HTML，文件名、`data-sec`、`<title>` 前缀三处一致（`2.3` → `2-3.html`）。
7. 换课程身份改 `tools/curriculum.py` 的 `MODULE`：`title`、`subtitle`、`mark`、`kicker`、`description`、`searchHint`、`lede`，以及**必须唯一**的 `progressKey` / `uiKey` / `progressFile`。
8. 不提交与课程无关的文件（预览图、缓存、`__pycache__`）。

### 二、每节的顺序（不能换）

```text
动机 → 推导卡 → 定义/定理 → 证明 → 图像 → 例题 → 算法落地卡 → 习题 → 一页纸
```

1. **先需求，后定义**：先给一个算不出来、判断不了、会出错的具体问题。
2. **先推导，后定理**：定理与正式证明必须排在推导卡之后，**不允许**先抛结论再补动机。
3. **先具体，后抽象**：至少用一个具体数字、表格、图像或手算过程解释抽象陈述。
4. **图不是装饰**：每幅图必须回答“看图该看出什么”。
5. **证明不是装饰**：指出关键跳步的依据，不写「显然」「易证」。
6. **算法不是附加题**：每个核心算法都要说明对应哪条定理、为什么正确、复杂度多少、边界在哪。

### 三、强制模块 A：定理前的「推导卡」

对每一个独立定理、引理、性质，在定理盒之前放一张 `推导` 卡；互相依赖的多个定理可共用一张，但卡头要写清「覆盖：定理 A / 定理 B」。

固定四段（缺一段 `check.py` 会报错）：

| 段 | 类名 | 写什么 |
|---|---|---|
| 卡头 | `.derive-h > .dk` + `<b>` + `.dsub` | 「推导」标签 + 「在知道某某定理之前」+ 节奏提示 |
| 问题 | `.derive-q` | 一个具体需求，能立刻动手算 |
| 步骤 | `.dstep > .dn` + `.dh` + `<p>` + `.dcheck` | 3–5 步：尝试 / 观察 / 构造 / 验证 |
| 落定理 | `.derive-end` | 「于是我们得到：……」→ 紧接着 `.thm` 与 `.prf` |

写作要求：先假设读者不知道这个定理；一步只做一件小事；每一步解释「为什么可以这样」；允许出现失败尝试。

```html
<div class="derive">
  <div class="derive-h"><span class="dk">推导</span><b>在知道“……”之前</b><span class="dsub">需求 → 尝试 → 验证 → 定理</span></div>
  <div class="derive-q"><b>问题</b>　……</div>
  <div class="dstep">
    <div class="dn">1</div><div class="dh">这一步做什么</div>
    <p>……</p>
    <div class="dcheck"><b>观察</b>　……</div>
  </div>
  <div class="derive-end"><b>于是我们得到：</b>……</div>
</div>
<div class="thm"><span class="tag">定理（……）</span><p>……</p></div>
<div class="prf"><span class="tag">证明</span><p>……<span class="qed">∎</span></p></div>
```

### 四、强制模块 B：定理后的「算法落地卡」

**凡是有算法价值或建模价值的定理/性质**，在定理与证明之后放一张 `算法落地` 卡（纯理论节可整段省略，但一旦出现 `.codebox` 就必须有 `.walk`）：

| 段 | 类名 | 写什么 |
|---|---|---|
| 卡头 | `.walk-h > .wk` + `<b>` + `.cover` | 「算法落地」+ 例子名 + 覆盖哪条定理 |
| 需求 | `.walk-req` | 一组能手算的输入 + 期望输出 |
| 拆步 | `.walk-step > .ws-h > .ws-n` | 3–5 步，每步对应定理的一步 |
| 每步代码 | `pre.snip` | 只做当前步骤的代码，变量名与数学符号对应 |
| 为什么 | `.ws-why` | 动机、构造理由、边界（0 / 负数 / 溢出） |
| 竞赛用法 | `.walk-oi` + `.tags` | 看到什么条件想到它、复杂度、常见坑 |

硬规则：**每一步都必须同时有 `pre.snip` 和 `.ws-why`**；代码不是“贴一份完整 AC 代码”，而是“证明步骤的可执行对应物”。

### 五、图像与代码

每节至少：

- **2 幅带图注的图**：`figure.plot`（函数图）或 `figure.fig`（几何示意 / 算法流程图）；**有代码就必须有 1 幅流程图**；
- **2 个例题**：第一个标准情形，第二个变式 / 反例 / 边界；
- **3 道习题**：每题先 `.idea`（思路）再 `.ans`（答案），最后一题可稍难；
- **1 个思考点** `.think`；**1 个一页纸** `.keybox`；
- **正文汉字 1200–3000**（低于 1000 直接判失败）。

代码：

1. C++17；`<` `>` `&` 必须转义成 `&lt;` `&gt;` `&amp;`。
2. 代码块用 `.codebox` + `.code-h` + `<pre class="code">`；高亮类 `.kw` `.ty` `.fn` `.st` `.nu` `.cm`。
3. 64 位乘法默认 `__int128`；取模、逆元、快速幂要处理负数与 `m = 1`。
4. 流程图节点类：`fnode` / `fnode-b` / `fnode-g` / `fnode-r` / `fnode-a`，边 `ar` / `ar-d`，标注 `flab`；节点必须能在代码里找到对应行。

### 六、算法竞赛视角

每节至少回答一次：这个定理在 OI 里“长什么样”？它把什么暴力复杂度降到什么？什么时候不能用？能和前后哪一节拼接？

禁止只写“这个定理很重要”“可以优化算法”这种空话。

### 七、排版与公式规范

- 数学盒子：`.def` / `.thm` / `.prf` / `.insight` / `.why` / `.note` / `.warn`，**一律以 `<span class="tag">…</span>` 开头**；
- 证明盒以 `<span class="qed">∎</span>` 收尾；
- 公式内 `<` `>` 写 `\lt` `\gt`，`&` 写 `&amp;`；行内 `$…$`，行间 `$$…$$` 独占一行；
- 图必须有 `figcaption`；表必须 `<table class="tbl">`；
- `h2` 的 id 必须是 `s1…sN` 连续；不手写 `id="bN"`（构建期注入）；
- 不留 `TODO` / `FIXME` / 「这里写」。

### 八、工作流

1. **读模板**：`README.md`、`tools/curriculum.py`、`tools/build.py`、`tools/check.py`、`sections/_骨架.html`、`sections/1-1.html`（纯理论范本）、`sections/2-1.html`（定理+算法范本）。
2. **定蓝图**：Part/Chapter/Section、参考书映射、算法清单、节型。
3. **搭骨架**：复制模板 → 改 `MODULE` → 写 `PARTS`/`CHAPTERS`。
4. **逐节写**：推导卡 → 定理/证明 → 图/例题 → 代码/流程图/落地卡 → 习题/一页纸。
5. **构建**：`python tools/build.py`。
6. **自检**：`python tools/check.py`，修到全部通过。
7. **渲染验收**：公式渲染、图显示、深色主题、390px 窄屏、检索、上下节导航。
8. **提交**：只提交课程目录，提交信息写清新增/改造的模块。

### 九、验收清单

- [ ] 当前分支正确、课程目录正确、**引擎三文件未改动**
- [ ] 每个定理前都有推导卡，定理与证明排在推导之后
- [ ] 每个核心定理有落地卡：需求 → 3–5 步 → 每步代码 → 为什么 → 竞赛用法
- [ ] 每节 ≥2 图（有代码则含 1 幅流程图）、2 例题、3 习题、1 思考点、1 一页纸
- [ ] 所有图有有效图注；所有证明有 ∎；公式无未转义 `<` `>` `&`
- [ ] `python tools/build.py` 无报错；`python tools/check.py` 全部通过
- [ ] MathJax 无渲染错误；深色主题、390px 窄屏、检索、上下节导航正常
- [ ] 正文汉字在 1200–3000 之间

### 十、输出格式

完成后输出：分支名与提交哈希 → 课程结构（Part/Chapter/Section 数量）→ 新增/修改模块清单 → 构建与自检结果 → 渲染验收结果 → 已知限制。

### 十一、禁止事项

- 不要先写完定理再补“推导”；推导必须在定理之前。
- 不要用「显然」「易证」跳过关键步骤。
- 不要只给完整 AC 代码而不拆步骤；也不要让代码步骤与证明步骤对不上。
- 不要用截图代替可编辑的 `figure.plot` / `figure.fig`。
- 不要为了省事删掉定义/证明/习题组件。
- 不要改 `style.css` / `app.js` / `theme.js` 来“适配”单个课程。
- 不要声称“验证通过”而没有实际运行 `build.py` 与 `check.py`。

## 四、质量标准示例：一节「定理 + 算法」的骨架

以 §2.1 中国剩余定理为例（本模板 `sections/2-1.html` 里的 gcd/Bézout 是同一套写法）：

| 位置 | 内容 |
|---|---|
| 动机 | 两份“按不同周期报数”的记录，怎么合并成一个答案？ |
| 推导卡 | 问题：解 $x\equiv2(3),x\equiv4(5),x\equiv1(7)$ → 步骤 1 枚举发现周期 15 → 步骤 2 造“开关” $A,B$ → 步骤 3 一般化 $M_it_i$ → 步骤 4 验证唯一性 → 落定理 |
| 定理 + 证明 | CRT 的构造与唯一性，∎ 收尾 |
| 图像 | `figure.plot` 画出三个剩余类在数轴上的交点；`figure.fig` 流程图画出合并算法 |
| 例题 | 例 1 手算三式合并；例 2 模数不互素时的相容性判断 |
| 代码块 | `merge(a1,m1,a2,m2)` 完整函数 |
| 落地卡 | 需求：用上面的数字走一遍 → 5 步，每步一段 `snip` + `ws-why` → 竞赛用法（exLucas / 多模数哈希） |
| 习题 | 5 题：2 道手算、2 道证明、1 道综合 |

## 五、“好课件”的判断标准

1. **学生能复述**：合上页面，能讲出「为什么需要这个定理」。
2. **学生能手算**：每个定理至少有一个能手算的小例子。
3. **学生能证明**：证明的每一步能对应到定义或前一条结论。
4. **学生能编码**：代码的每一步能对应到证明的一步。
5. **学生能迁移**：知道这条定理在竞赛题里“长什么样”。

> 一条内容如果只满足“考试会写”，却说不清“为什么”，就没有达到本模板的要求。
