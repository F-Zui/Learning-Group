01 · 输入输出与评测机制

先把「题目 → 程序 → 评测」这条最短的链路走通：弄清评测机到底在比什么，看懂 cin / cout / getline 三个出入口，再第一次学会拿数据范围反推变量该开多大。
入门预计 45 分钟cin/coutgetline整数范围评测机制
本节出现的新函数 / 新语法（先看懂再用）
  • cin（标准输入流） —— 最常用的读入方式：自动跳过空白，按变量类型解析每个数
  • cout（标准输出流） —— 输出的主力：<< 把内容接进流里，用 "\n" 结束一行
  • ios::sync_with_stdio(false) 与 cin.tie(nullptr) —— 两行提速开关，输入量大时必写
  • getline（读入一整行） —— 需要保留空格时唯一靠得住的工具

先接受一个事实：评测机并不知道你想表达什么。它把你的程序输出的那串字节收下来，和标准答案的字节一个一个地比，完全相同才算通过。所以从今天起，每写一句输出都先问自己——这些字节会不会原封不动地出现在标准答案里？多一个空格、少一个换行、多一句“请输入”，都算错。

这一节只做三件事：把输入输出的三个工具拆开看清楚；用一道最简的 A+B 把「读入 → 计算 → 输出 → 返回」跑一遍；最后弄明白为什么变量类型要跟着数据范围走。它们看起来简单，却是后面每一道题都要重复几十遍的动作。

推导cin（标准输入流）：一句话把字节流切成一个个值覆盖：cin >> 变量 / 链式提取 / 类型解析需求 → 尝试 → 验证 → 定理
问题题面只写了一句「输入两个整数 a、b」，可程序手上只有两个空变量，输入文件里则是一整条字节流 2 3。谁负责把它切成第一个数、第二个数？它又凭什么知道该在哪里停？
1先把需求翻译成两个动作：取值、存变量

需求其实只有两件事——从输入里取出一个值，把它放进一个变量。C++ 把这两件事压成一个运算符 >>，箭头朝变量，读法是「流里的东西流进变量」：

std::cin >> 变量1 >> 变量2 >> ...;

这就是 cin 的全部签名。左边固定是流对象 std::cin，中间可以串任意多个 >>，右边每多写一个变量就多取一个值，取的顺序就是写的顺序。

2再把这句话拆成三段：流、运算符、变量各要求什么

签名看懂了不等于会用。三个位置各有硬性要求，写错任何一处，读进来的东西都不可信：

组成含义 / 格式要求
std::cin标准输入流对象，背后连着评测时喂给程序的那个输入文件。整个程序只有一个，直接用。
>>提取运算符，箭头朝变量：把流里的下一个“词”解析成右边变量的类型，再存进去。
链式写法cin >> a >> b 从左往右算：先得 (cin >> a)，它返回 cin 本身，于是能接着 >> b。写成两条语句完全等价。
跳过空白空格、Tab、换行都算分隔符，会被自动吃掉。所以“一行两个数”和“两行各一个数”读起来没有区别。
类型决定解析给 int 读整数，给 double 读小数，给 char 读一个非空白字符。类型写错，读进来的东西就不可信。
验证 / 关键链式写法能成立，靠的是一条返回规则：(cin >> a) 的结果就是 cin 本身，所以后面能接着 >> b。写成 cin >> a; cin >> b; 完全等价，一个值都不会少读。
3拿一段最小程序验证：读进来，再原样写出去

语法对不对，跑一遍最清楚。这段程序读两个整数、输出它们的和，正好把「读—算—写」走一遍：

#include <iostream>
using namespace std;

int main() {
    int a, b;
    cin >> a >> b;              // 一次取两个整数
    cout << a + b << "\n";
    return 0;
}

把输入写成两行（先 2、换行、再 3），输出仍然是 5——这就验证了「跳过空白」这条规则：对 >> 来说，空格和换行是同一件东西。

4最后验证失败的那条路：类型不对、数据不够

上面每一步都默认输入合法，而真正的坑全在失败路径上——cin 的失败是静默的，不抛异常、不打印任何东西：

验证 / 关键

变量类型必须和输入对得上：让 int 去读 abc，cin 会读失败，并且此后所有读入都静默失效——它不报错，只是把垃圾值留在变量里。

cin 也不检查你读够了没有。数据比预期少时，后面的变量保持原值；局部变量是未初始化的，那是个随机数。

于是我们得到：cin >> x 一句话做三件事——跳过前面的所有空白、按 x 的类型解析一个值、把值存进 x。所以类型必须和输入对得上；它也从不为失败报警，只会把后面的读入一起废掉。
推导cout（标准输出流）：把值变成字节，一个不多一个不少覆盖：cout << 内容 / 格式控制 / 提速两行需求 → 尝试 → 验证 → 定理
问题算出来的和还躺在内存里，评测机却只认输出文件里的那串字节。怎么把一个 int 变成 5 这一个字符？多打一个空格、少打一个换行，逐字节比对就会判错——这些格式又该由谁决定？
1需求 → 一句话：把值一个个接进输出流

输出的动作和输入正好镜像：这次是「变量里的东西流进流里」，所以箭头朝流：

std::cout << 内容1 << 内容2 << ...;

插入运算符能连着写任意多个，插进去什么类型就按什么类型转成字符，不必像 printf 那样先背一串格式符。

2拆开看：每个位置各管什么

这几行里，前两行决定「写什么」，中间几行决定「写成什么样」，最后一行是数据量大时的提速开关：

组成含义 / 格式要求
std::cout标准输出流对象。评测时它被接到一个文件上，程序结束后整份文件拿去和标准答案比对。
<<插入运算符，箭头朝流：把右边的值转成字符送进去。它的方向和 >> 正好相反，别写反。
"\n"一个换行字符。只往缓冲区塞一个字节，几乎不花时间，是最省事的收尾方式。
endl换行 + 立刻刷新缓冲区。循环里用上百万次会慢一个数量级，多出来的开销全在 flush 上。
fixed << setprecision(3)保留 3 位小数，需要 #include <iomanip>。不加 fixed 时，setprecision 数的是有效数字位数，完全不是一回事。
提速两行输入输出量大于 10⁵ 次时，在 main 开头写 ios::sync_with_stdio(false); cin.tie(nullptr);：关掉 C 流与 C++ 流的同步、解除 cin 对 cout 的绑定。写一次就够，之后不要再混用 scanf / printf。
验证 / 关键<< 的返回值和 >> 一样是流本身，所以能一路链下去；而 endl 等价于「一个 '\n' 加一次强制刷新」，循环里用它等于每行都催一次缓冲区。
3拿一段最小程序验证：整数原样打、小数位要自己设

这段程序一次演示三件事：整数照原样打、数字之间的空格要自己补、浮点的小数位要手动设：

#include <iostream>
#include <iomanip>
using namespace std;

int main() {
    int a = 2, b = 3;
    cout << a << ' ' << b << "\n";                        // 输出 2 3

    double ans = 500.0 / 3;
    cout << fixed << setprecision(3) << ans << "\n";   // 输出 166.667
    return 0;
}
验证 / 关键最后一行输出 166.667。把 fixed 删掉再跑一次，输出会变成 167——此时 setprecision(3) 数的是有效数字，不是小数位数。
4两条边界：格式要自己说清楚、循环里别用 endl

cout 不会替你补小数点、不会替你四舍五入，也不会替你判断该不该换行。两条最容易踩的规矩：

验证 / 关键

cout 不需要写格式符，插进去什么类型就按什么类型打；但也正因为如此，它不会替你补小数点、也不会替你四舍五入，格式必须自己说清楚。

循环输出十万行以上时，一律用 "\n"，不要用 endl。

于是我们得到：cout << x 只负责把 x 按类型转成字符，格式（小数位、宽度、换行）一律要自己说清楚；输出量大时一律写 "\n"，把 flush 留给程序结束前的那一次。
推导getline（读入一整行）：空格也要留下的场合覆盖：std::getline / 停止条件 / 残留换行需求 → 尝试 → 验证 → 定理
问题这一次要读的不是一个数，而是一整行带空格的句子。用 cin >> s 试一下就会发现：它停在第一个空格处，只拿到一个「词」。怎么才能把空格一起读进来？
1需求 → 换一个工具：按行读，不按词读

>> 的设计目标就是「跳过空白、取一个值」，它天生拿不到空格。要整行，得用一个独立的函数，把流和一个 string 交进去：

std::getline(std::cin, s);

它是标准库里的普通函数，声明在 <string> 而不是 <iostream> 里——头文件少写一个，编译直接失败。

2拆开看：谁读、读进哪、读到哪停
组成含义 / 格式要求
std::getline独立的函数，声明在 <string> 里，不是 cin 的成员。所以头文件别只写 iostream。
std::cin第一个参数：从哪个流读。考试里永远是 cin。
s第二个参数：一个 string 变量，整行内容写在这里，不含行末的换行符。
读到哪里停一直读到 '\n' 为止，并且把这个换行符从流里取走丢掉，所以下一次读入不会莫名其妙读到空行。
和 cin >> 的区别cin >> 在第一个空白处就停，只拿到一个“词”；带空格的句子必须用 getline。
要不要 ignore刚用 cin >> 读过一个数，流里还留着一个换行，getline 会立刻读到空串。中间补一句 cin.ignore(); 就对了。
验证 / 关键停止条件是「读到换行」，并且这个换行会被读走丢掉。所以连续两次 getline 读到的正是两行，第二次不会莫名其妙得到一个空串。
3拿一段最小程序验证：先读数，再读整行

这段程序先读一个整数，再读一整行，最后用方括号把读到的行括起来——空格有没有保留，一眼可见：

#include <iostream>
#include <string>
using namespace std;

int main() {
    int n;
    string line;
    cin >> n;                  // 先读一个整数，换行留在流里
    cin.ignore();            // 吃掉那个换行，否则下一行读到空串
    getline(cin, line);       // 再整行读入，空格一起留下
    cout << n << " [" << line << "]\n";
    return 0;
}
验证 / 关键把 cin.ignore(); 删掉再跑，方括号里会变成空的：整数后面残留的那个换行，被 getline 当成了整行的结束。
4两条边界：残留换行，以及读完别再拿 >> 去切

getline 本身没有毛病，出问题的一定是它前面那一步：

验证 / 关键

读到的空串不是 getline 的毛病，是 cin >> 读完后残留的那个换行没被处理。加上 ignore 就恢复正常。

getline 会把空格一起读进来，所以读完之后不要再拿 >> 去切它，要么用 stringstream，要么自己扫一遍字符。

于是我们得到：getline(cin, s) 读到换行为止、并把换行从流里取走，整行内容（含空格）原样进 s。它唯一的脾气是「前一步留下的换行也算一整行」，所以读数之后再读行，中间要补一句 cin.ignore()。
算法落地A+B：把「读—算—写」落进一个完整程序覆盖：洛谷 P1001 / 输入输出三件套
需求

例题 · A+B Problem · 洛谷 P1001 入门

输入两个整数 a、b（|a|,|b| ≤ 10⁹），输出它们的和。

题面就这么一句话，却是整门课的第一块砖：输入不过三个字符 2 3，输出只有 5，任何多余的字符都会被逐字节比对当场抓出来。

样例
输入：
2 3
输出：
5
1声明两个整数：先有位置，再谈读入

程序要接住两个数，先得有两个能装 32 位整数的位置：

int a, b;              // ① 两个 32 位整数，此刻值不确定
为什么两个 int，各占 4 字节。C++ 不保证局部变量被清零，此刻 a、b 里是内存中残留的字节，所以必须先读再用——拿没读过的值去算，答案一定是垃圾。
2按题面顺序读入：一个 >> 一个变量
cin >> a >> b;         // ② 按顺序把两个整数取进来
为什么先给 a 取第一个整数，再给 b 取第二个；两个数之间是空格还是换行，cin 不在乎，它只认「下一个值」。顺序必须和题面一致——写反了，加法还看不出问题，一遇到减法或输出 a、b 就立刻错。
3把和算出来：先存住，再输出
int s = a + b;         // ③ 相加，结果先存着
为什么用一个新变量接住和。本题最大和 2×10⁹，int 上限 2147483647，放得下；但余量只剩 1.47×10⁸，所以数据范围要看清——范围放大一倍，这里和 a、b 就要一起换成 long long，只换接收结果的变量没有用。
4写出去：只写数字和换行
cout << s << "\n";     // ④ 只写数字和换行
为什么把 s 转成十进制字符串写进输出流，末尾补一个换行。'\n' 是一个字符，不是反斜杠加 n 两个字符。任何「答案是」这样的说明文字都会变成答案的一部分，直接 WA。
5补齐入口与出口：完整程序

四步拼起来，再加上头文件、命名空间、main 和返回值，就是能直接提交的完整程序：

#include <iostream>
using namespace std;

int main() {
    int a, b;              // ① 两个 32 位整数，此刻值不确定
    cin >> a >> b;         // ② 按顺序把两个整数取进来
    int s = a + b;         // ③ 相加，结果先存着
    cout << s << "\n";     // ④ 只写数字和换行
    return 0;              // ⑤ 正常结束
}
为什么

#include <iostream> 引入标准输入输出库，cin 与 cout 的声明都在这里，删掉这一行，编译第一行就失败；using namespace std; 把 std 里的名字拉到全局，于是能写 cin 而不是 std::cin。

int main() 是程序入口，评测系统从这里开始跑；return 0; 是正常退出的约定，退出时输出缓冲区被整体刷出去，评测机这才开始逐字节比对。不写多数编译器会替你补，但别把这种运气当规范。

竞赛用法

题型特征：读一组数、输出一个结果的送分题，真正的考点从来不在算法，而在格式——读几个、按什么顺序读、输出几行、每行什么形状。凡是「样例过了还是 WA」，先怀疑这一层。

复杂度：O(1) 时间、O(1) 空间。这道题的时间限制没有意义，WA 一定出在字节上，不会是 TLE。

  • 输出提示语：多写一句「请输入两个数：」，整串字节就和标准答案对不上了。
  • 行末多打空格：5 和 5 是两条不同的字节流，严格评测直接 WA。
  • 忘记换行：多数题不敏感，但逐行比对的题会把最后一行判成格式错误。
  • 用 int 硬扛可能超范围的和：范围一放大就溢出成负数，拿不准就用 long long。

可扩展：同一套骨架换成「读 n 个数求和」「读一行字符串再处理」，变的只是读入与输出的形状，三段式的顺序一条都不用改。

模型：读—算—写三件套O(1) 时间 / O(1) 空间坑：行末空格与提示语
这一节最容易犯的 4 个错

输出提示语。写 cout << "请输入两个数：" 会直接 WA——评测机不读中文，它只看到一个比标准答案长很多的字节流。

用 int 硬扛可能超范围的和。本题刚好卡在 2×10⁹，再大一点（|a|,|b| ≤ 2×10⁹ 时 a + b 能到 4×10⁹）就溢出成负数。写之前先看数据范围，拿不准就用 long long。

忘记换行。多数题对行末换行不敏感，但有些题逐行比对，最后一行没有换行会被判格式错误。

行末多打空格。5 和 5 是两个不同的字节流，严格评测（例如 NOIP）直接 WA。数字之间该空格就空格，行末只留换行。

自己动手复现

合上这一页，凭记忆把上面那段 A+B 完整代码敲一遍，编译运行，输入 2 3，确认输出是 5 而不是别的东西。

把输入换成 1000000000 1000000000，输出应该是 2000000000；再换成 -1000000000 -1000000000，输出应该是 -2000000000。两次都对了，说明你读入和输出的顺序都没写反。

然后把 int a, b; 改成 short a, b;，然后用同一个输入再跑一次——你会看到一个和 2000000000 毫不相干的数。那就是溢出，下一节正式讲它。

最后提交到 P1001。如果 WA，先把自己的输出和标准答案逐个数一遍字节，别急着改算法——这一题的算法只有一行。

数学补给 · 为什么 int 的上限是 2.1×10⁹

现在主流的编译器和评测机上，int 都是 4 字节 = 32 个二进制位。计算机用补码存负数，最高位是符号位：0 表示非负，1 表示负。

剩下 31 位用来表示大小，能区分 2³¹ = 2147483648 个不同的非负值，从 0 数到 2147483647。所以最大值 = 2³¹ − 1 = 2147483647 ≈ 2.147×10⁹，最小值 = −2³¹ = −2147483648。

负数比正数多一个，是因为补码里 0 只有一种写法（全 0），空出来的那个编码被拿去表示最小的负数。于是正负加起来正好 2³² 个数，一个不多、一个不少，这才叫“不浪费任何一种编码”。

心算记法。2¹⁰ = 1024 ≈ 10³，于是 2³¹ = 2 × (2¹⁰)³ ≈ 2 × 10⁹。这个近似值足够回答“这题要不要开 long long”：题目里出现的量级超过 10⁹，就别用 int 存答案；到 10¹⁸ 量级必须 long long。

类型字节范围十进制位数
short2−32768 ~ 327675 位
int4−2147483648 ~ 214748364710 位
unsigned int40 ~ 429496729510 位
long long8−9.22×10¹⁸ ~ 9.22×10¹⁸19 位

一句话结论：先看数据范围，再定变量类型。long long 的加减乘比 int 慢一点点，在竞赛的量级上几乎察觉不到，宁可多开一个字节都不该赌。真正贵的是溢出之后重新提交、重新怀疑算法的那半小时。

    理由：评测机把两份输出当字节流逐字节比较，它不解析语义，也不会替你删前缀或忽略空格。第一个不一致的位置就是判错的起点。
    常见错路：拿样例对眼睛。人看“answer = 5”觉得内容对了，机器比的是第 1 个字节 'a' 和第 1 个字节 '5'——从一开始就不一样。
  2. 先 cin >> n，再 getline(cin, s)，为什么 s 是空串？怎么改？
    想好了？点开核对思路与解析
    结论：cin >> n 在第一个非数字字符处停下，那个换行还留在流里；getline 一进流就撞上它，于是立刻返回一个空串。
    理由：getline 的停止条件正是“读到换行”，读到就返回，并把这个换行从流里取走。而此刻缓冲区里的第一个字符，恰好是上一次读整数时没被消耗掉的换行。
    改法：两者之间加一句 cin.ignore();，默认吃掉一个字符；数据行可能带多余空格时，写成 cin.ignore(…, '\n') 把整行残余清干净。
    常见错路：以为 getline 坏了，换成 cin >> s——那样带空格的句子会在第一个空格处被截断，错得更隐蔽。
  3. 输入写成 2 3（同一行）和 2 换行 3（两行），对 cin >> a >> b 有区别吗？
    想好了？点开核对思路与解析
    结论：没有区别，两种写法都能正确得到 a = 2、b = 3。中间夹几个空行也一样。
    理由：提取运算符把空格、Tab、换行一视同仁地当分隔符，先跳过所有空白，再解析下一个值。所以在它眼里，“换行”和“空格”是同一个东西。
    常见错路：以为“按行给的数据必须按行读”，于是先 getline 再自己拆——不但麻烦，还容易栽在残留换行上。另一种错路是反过来，以为 cin 会检查格式，其实输入里多写几个空格它照样算对。
  4. 题目说 |a|,|b| ≤ 10⁹，用 int 存 a + b 真的安全吗？边界在哪？
    想好了？点开核对思路与解析
    结论：安全。最大的和是 2×10⁹ = 2000000000，比 2147483647 还小 1.47×10⁸。
    理由：只有两个 10⁹ 同号相加才可能顶到上限，而 2×10⁹ 与 2.147×10⁹ 之间确实留了余量。余量很小，所以在草稿纸上写下“2×10⁹ < 2.147×10⁹”这一步不能省。
    常见错路：把“这题能过”当成“int 永远够用”，下一道题照抄 int 就翻车；还有一种是算 (l + r) / 2 求中点时，l、r 都接近上限，相加先溢出，后面除法再准也没用——正确写法是 l + (r - l) / 2。

挑战题 · 再分肥宅水
洛谷 P5706入门去洛谷做这题 ↗

有 t 毫升肥宅快乐水，要平均分给 n 名同学，每名同学再发 2 个杯子。求每人能分到多少毫升，以及一共要准备多少个杯子。

输入一行两个数 t、n（0 ≤ t ≤ 10⁴，1 ≤ n ≤ 10³），t 可能是小数，n 一定是整数。

输出两行：第一行是每人分到的毫升数，保留 3 位小数；第二行是一个整数，表示杯子的总数。

样例 · 先手算，再对照程序输出
输入： 500.0 3 输出： 166.667 6
引导性提示（先只看这里）

这是两个互不相干的问题：一个是实数除法，一个是整数乘法。不要试图用一句 cout 把它们一起打出来。

“保留 3 位小数”不是“四舍五入到 3 位有效数字”。cout 里管这两件事的是两个不同的东西，少写一个，结果就从 166.667 变成 167。

第二行是整数乘法，别写成 2.0 * n——那样它会被上一行的格式设置带成 6.000。

想看思路了？点开完整思路

第一问：每人分到 t / n 毫升。t 用 double 读，n 用 int 读，二者相除自动按实数算。输出要 3 位小数，写法是 cout << fixed << setprecision(3) << t / n。

第二问：每名同学 2 个杯子，n 名同学就是 2n 个。n ≤ 1000，2n ≤ 2000，int 绰绰有余，不需要任何技巧。

两行输出，各带一个换行。第一行设好的小数格式会一直保持，但它只作用于浮点数，所以第二行仍然是一个干干净净的整数。

为什么不能合成一句：两问一个是浮点、一个是整数，混在一个表达式里既改不了中途的格式，也容易把杯子数打成小数。分开写，一段话对应一行输出，读代码的人（包括三天后的你）一眼就能对上题面。

还是不会？点开题解代码与拆解
参考代码
#include <iostream>
#include <iomanip>
using namespace std;

int main() {
    double t;
    int n;
    cin >> t >> n;

    cout << fixed << setprecision(3) << t / n << "\n";  // 每人分到的毫升数
    cout << 2 * n << "\n";                          // 杯子总数

    return 0;
}
关键片段拆解
片段作用
#include <iomanip>setprecision 声明在这个头文件里。只引 iostream 会得到“未声明的标识符”，编译直接失败。
double t; cin >> t;t 可能是 500.0 这种带小数点的数。用 int 读会在小数点处停下，后面所有读入跟着错位。
fixed切成定点表示。不加它，setprecision(3) 数的是有效数字：500/3 会输出 167，样例当场对不上。
setprecision(3)配合 fixed 表示“小数点后 3 位”。它对之后的输出一直生效，所以要在这句之后的第一次输出就用上。
t / nt 是 double、n 是 int，自动转成 double 再除，得到实数除法 166.6666…；若两个都是 int，除出来的 166 会把小数位全丢掉。
2 * n整数乘法，输出 6。上一行的 fixed 只影响浮点数，不会把它变成 6.000——但写成 2.0 * n 就会了。
"\n"两行都要换行。第一行漏了，两个答案会粘成 166.6676，样例一跑就露馅。
