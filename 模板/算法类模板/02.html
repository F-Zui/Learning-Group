02 · 循环、累加与整数溢出

把「算一次」变成「算一千万次」：用 for 和 while 把重复劳动交给机器，用累加器把每一轮的结果攒成一个数，并且在动手写代码之前先算清这个和会不会撑破 int 的 21 亿。
入门预计 50 分钟for / while累加器long long整数溢出
本节出现的新语法（先看懂再用）
  • for 循环 —— 次数已知时用它，三段式把「从哪开始、什么时候停、每轮怎么变」写在同一行里
  • while 循环 —— 次数未知时用它，循环体里必须有一句让条件最终变假
  • 累加器 —— sum += x 这一行，把每一轮的结果攒进同一个变量
  • long long —— 装得下 19 位整数的类型，求和之前先估上界，再决定要不要换它

第 1 节的程序只算一次：读一个数、算一次、输出。这一节要让程序算一千万次，但代码一行都不多加——循环的全部作用就是把「重复」这件事交给机器。拆开看只有三个问题：从哪里开始、什么时候停、每一轮做什么。想不清这三个问题，写出来的不是死循环就是差一项。

先算次数，再算范围。次数决定会不会超时，范围决定答案对不对。

这两件事经常被混成一件。本节例题的循环要跑一千万圈，这是「多不多」的问题；而那个和的答案有 5×10¹³ 那么大，这是「装不装得下」的问题。前者算错，程序跑到超时被判 TLE；后者算错，程序按时跑完却输出一个负数，被判 WA。两类错误的症状、排查方向、修改位置全都不同，所以从一开始就分开算。

算法落地1 + 2 + … + n：一次循环把一千万项收进一个变量覆盖：洛谷 P5722 / 循环累加
需求

例题 · 数列求和 · 洛谷 P5722 入门

给定一个正整数 n，求 1 + 2 + 3 + … + n 的值。

输入格式：一行一个正整数 n（1 ≤ n ≤ 10⁷）。输出格式：一行一个整数，表示这个和。

本题的 n 只到一千万，所以「一项一项加」完全跑得动，就用循环写；等差数列公式 n(n+1)/2 放在本节末尾的数学补给里，用它来验算和估范围，不用它来替代循环。

样例
输入：
100
输出：
5050
1读入 n：类型按「最大可能值」定
long long n;
cin >> n;                                  // 1 <= n <= 1e7
为什么

n 最大 10⁷，int 装得下。这里仍写 long long，是为了让 i <= n 两边的类型一致，不出现隐式转换这种需要额外解释的东西。

读入一行一个整数，换行符会被自动跳过，不用额外处理。

2备一个累加器：初值必须是 0
long long sum = 0;                         // 累加器：初值必须自己写 0
为什么初值 0 是加法的单位元：0 + x 还是 x。漏掉 = 0 时，局部变量里是栈上残留的随机值——同一份代码跑两次结果都可能不同，小数据碰巧对、大数据稳定错。
3把 n 项扫一遍：for 的三段式
for (long long i = 1; i <= n; ++i) {       // 初始化 / 判断 / 每轮末尾 ++i
    sum += i;                              // 循环体：把第 i 项加进去
}
为什么

从 1 起步、到 n 为止、每轮加 1。<= 决定 n 也在里面，一共 n 轮；写成 < 就只有 n−1 轮，最后一项被关在循环外面。

sum += i; 是循环体唯一一句，被执行 n 次，等价于手写 n 行加法。循环结束后 i 就失效了，花括号后面不要再拿 i 当第 n 项用。

4输出：写在循环外面，只写一次
cout << sum << "\n";                      // n 项都加完了，输出
为什么循环外面的语句只执行一次，此时 sum 已经攒完 n 项。写进循环体里就会打印 n 行中间结果，答案格式全错。
5补齐入口与出口：完整程序

五段拼起来，再加上万能头文件和 return 0;，就是能直接提交的一份程序：

#include <bits/stdc++.h>
using namespace std;

int main() {
    long long n;
    cin >> n;                                  // 1 <= n <= 1e7

    long long sum = 0;                         // 累加器：初值必须自己写 0
    for (long long i = 1; i <= n; ++i) {       // 初始化 / 判断 / 每轮末尾 ++i
        sum += i;                              // 循环体：把第 i 项加进去
    }

    cout << sum << "\n";                      // n 项都加完了，输出
    return 0;
}
为什么

#include <bits/stdc++.h> 是万能头，一次顶掉 iostream、climits 这些零碎头文件，竞赛里几乎每份代码都用它。

return 0; 告诉评测机程序正常结束：退出时输出缓冲区被整体刷出去，评测机这才开始逐字节比对答案。

竞赛用法

题型特征：看到「求 1 到 n 的和」「把 n 个数加起来」「数一数有多少个满足条件」，先想「累加器 + 单层循环」这个骨架。它的标志是每一轮做的事完全一样，只是下标在变。

复杂度：O(n) 时间、O(1) 空间。n = 10⁷ 时约 10⁷ 次加法，十几毫秒；n 一旦涨到 10⁹，同样的代码要跑好几秒，那时必须换公式或者换算法，而不是把循环写得更紧。

  • 累加器不初始化：结果是栈上的随机值，样例小的时候还可能碰巧对上。
  • 边界差一次：i < n 只有 n−1 轮，n = 1 时直接输出 0。
  • 用 int 求和：加到 65536 就翻成负数，样例（n = 100）完全正常。
  • 乘法先溢出再赋值：long long ans = a * b; 先按 32 位乘完，残值才转成 64 位。

可扩展：求积把初值换成 1；求最大值时初值不能随手写 0（数据可能全是负数），要写成 −INF 或者第一个元素。

模型：单层循环 + 累加器O(n) 时间 / O(1) 空间坑：边界差一项与 int 溢出

题面读完了，先别写代码。下面三张卡分别讲「怎么重复」「什么时候停」「用什么类型装」，每张都配一段能直接编译运行的示例；看完再回到这道题，代码只是把这些零件拼起来。

推导for 循环：把「重复」压成一行三段式覆盖：for (初始化; 条件; 步进) / 循环体 / 轮数需求 → 尝试 → 验证 → 定理
问题要把「1 加到 100」写成代码，手写 100 行显然不现实。可就算让机器来重复，也得先回答三个问题：从哪个数开始、什么时候停、每一轮怎么变。三个问题分散在三个地方写，改一个漏两个，循环就废了。
1需求 → 把三件事塞进同一行：初始化、条件、步进

既然三个问题必须一起回答，那就在同一行里回答。for 的括号里用两个分号切成三段，正好对上三个问题：

for (初始化; 条件; 步进) { 循环体 }

括号里的三段只管「转几圈」，花括号里的循环体才是「每圈做什么」。两件事分开写，改轮数不会动到循环体。

2拆开看：三段各在什么时候执行

这一行之所以能表达「重复」，靠的是三段各自的执行时机——初始化只做一次，条件每圈问一次，步进每圈末尾做一次：

组成含义 / 格式要求
初始化进循环之前只执行一次，通常写 int i = 1。循环变量在这里诞生，也只在这层循环里有效。
条件每一轮开始前检查一次，为真才进循环体。i <= n 配从 1 起步，正好是 n 轮。
步进每轮循环体结束后执行。++i 与 i++ 写在这里等价，换成 i += 2 就变成隔一个取一个。
两个分号三段之间用分号隔开，不是逗号，一个都不能省。
循环体只有一句也写花括号，以后往里加第二句时不会漏掉边界。
验证 / 关键轮数由「条件」单独决定，和循环体写了什么无关：i <= n 配 i = 1 起步正好 n 轮。写完拿 n = 1 代一遍，能进一圈就说明边界写对了。
3拿一段最小程序验证：累加 100 项、再从 0 数到 4

这段程序跑两个循环：第一个验证「从 1 加到 100」，第二个验证「从 0 起步要写 i < 5」：

#include <bits/stdc++.h>
using namespace std;

int main() {
    long long sum = 0;
    for (int i = 1; i <= 100; ++i)
        sum += i;                          // 循环体：加进去，然后回到条件
    cout << sum << "\n";             // 5050

    for (int i = 0; i < 5; ++i)
        cout << i << " ";             // 0 1 2 3 4，从 0 起步就写 i < 5
    cout << "\n";
    return 0;
}

两次输出分别是 5050 和 0 1 2 3 4。数一下第二行有几个数，就知道 i < 5 为什么是 5 轮。

4两条边界：差一项、以及步进和条件对着干

for 的 bug 几乎都能归到「轮数不对」这一类，而轮数只由条件和步进决定：

验证 / 关键

条件里的边界符号直接决定轮数：i <= n 是 n 轮，i < n 只有 n−1 轮。写完先拿 n = 1 试一次——正确答案是 1，程序输出 0 就说明少了一轮。

步进别和条件对着干：i <= n 配 i += 2 而 n 是奇数时，i 会从 n−1 直接跳到 n+1，这一轮白漏；把条件写成 i != n 再配 i += 2，就是永远退不出。

于是我们得到：for (初始化; 条件; 步进) 把「起点、终点、步长」钉在同一行：初始化只做一次，条件每圈判一次（为真才进循环体），步进每圈末尾做一次。轮数由条件和步进共同决定，所以边界只用在这两处检查。
推导while 循环：只知道「转到什么状态该停」的时候覆盖：while (条件) / 让条件变假 / break 与 continue需求 → 尝试 → 验证 → 定理
问题有些过程根本数不清要转多少圈——比如「n 是偶数就除以 2、是奇数就变 3n+1，直到 n = 1」，转几圈要跑起来才知道。for 的三段式连「总共几轮」都写不出来，这时候怎么写？
1需求 → 只写「停的条件」，不写轮数

把 for 的三段砍成一段：既然不知道轮数，就只保留「每圈开始前问一次」的那个条件，其余交给循环体自己推进：

while (条件) { 循环体 }

没有初始化段、也没有步进段。这两件事不是消失了，而是被挪进了循环体——所以写 while 时，脑子里必须一直记着「谁负责让它停下来」。

2拆开看：五个关键词各管什么
组成含义 / 格式要求
while每一轮开始前检查条件，为真就再转一圈。没有初始化段和步进段，全靠自己写。
何时用次数未知时用它：不知道要转几圈，只知道转到什么状态就该停。
让它变假循环体里必须有一句改变条件里的量，否则条件永远为真，程序卡死 → TLE。
break立刻跳出整个循环，适合「找到就停」。循环末尾的语句一句都不再执行。
continue跳过本轮剩下的语句直接进下一轮判断。for 里它会先做步进，别和 while 混着理解。
验证 / 关键for 也能写成 while：for (int i = 1; i <= n; ++i) 等价于「先写 int i = 1;，再 while (i <= n) { ...; ++i; }」。反过来则不一定——不知道轮数的循环，for 的三段里没地方写。
3拿一段最小程序验证：27 要多少步才掉到 1

这段程序把 while 的「条件 + 推进」写全了：条件是 n != 1，推进是循环体里那两支：

#include <bits/stdc++.h>
using namespace std;

int main() {
    long long n;
    cin >> n;                    // 输入 27

    int step = 0;                 // 计数器：每轮只加 1 的累加器
    while (n != 1) {             // 停的条件是 1，不是 0
        if (n % 2 == 0) n /= 2;       // 偶数折半
        else n = 3 * n + 1;          // 奇数变 3n+1
        ++step;                     // 走哪一支都要记一步
    }

    cout << step << "\n";          // 输出 111
    return 0;
}

跑出来是 111：从 27 出发，111 步之后才第一次等于 1。这个数事先谁也算不出来，正是「轮数未知」的典型。

4两条边界：谁让条件变假、条件写错一位

while 的 bug 只有一类：条件永远为真。写之前先指着循环体回答一句「哪一行会让它变假」：

验证 / 关键

写 while 之前先回答一句话：循环体里哪一行会让条件变假？答不出来就会写出死循环。上面这段里变的是 n，而 n /= 2 与 n = 3 * n + 1 两支都在缩小或推进这个数。

条件写错一位就换个故事：写成 n > 0 的话 n 永远为正，程序一直转到溢出为止。反过来写成 n != 0 又会在 n 恰好跳到 0 时停住——而这道题的出口是 1。

于是我们得到：次数已知用 for，三段写在一行里不容易漏；次数未知用 while，只写「停的条件」，并且循环体里必须有一句真的在推进它。回答不出「哪一行让条件变假」，写出来的就是死循环。
推导long long 与整数溢出：答案装不下时会发生什么覆盖：int / long long 的范围 / 上界估算 / 中间量需求 → 尝试 → 验证 → 定理
问题循环写对了，累加器也初始化了，样例 5050 一分不差。可 n 换成 10⁷ 时，正确答案是 5×10¹³，而 int 只装得下 2.1×10⁹。这个和到底该用什么类型装？装不下的那一刻，程序会怎样？
1需求 → 先看两个候选类型的容量

能装整数的类型不止一个，它们的区别只在「几位」。把这行当成签名读：左边是类型，右边是它能装到的上限：

int        // 32 位，上限  2147483647
long long  // 64 位，上限  9223372036854775807

选类型不是看「数有多大」，而是看「算出来的量最大能有多大」——本题的答案是 n(n+1)/2，不是 n。

2拆开看：范围、怎么估、什么时候换
组成含义 / 格式要求
int 的范围−2147483648 到 2147483647，约 ±2.1×10⁹，十位数。超出去不会报错，只会把高位丢掉、绕回负数。
long long 的范围约 ±9.22×10¹⁸，十九位数。日常题目里「装得下 10¹⁸」就够了。
怎么估一个乘法：项数 × 单项最大值。1..n 的项数是 n、单项最大是 n，所以上界约 n²/2。
什么时候换上界超过 2.1×10⁹ 就用 long long。拿不准时先换——多占 4 个字节，不会更慢。
乘法陷阱a * b 的类型由 a、b 决定，和左边接收它的变量无关；要写 1LL * a * b 把整个式子抬到 64 位。
验证 / 关键估算只要一个乘法：项数 × 单项最大值。1..n 有 n 项、最大项是 n，所以上界约 n²/2；n = 10⁷ 时就是 5×10¹³，比 int 上限大两万多倍。
3拿一段最小程序验证：同一个循环，两种累加器

这段程序用同一个 n = 65536 跑两遍，只换累加器的类型：

#include <bits/stdc++.h>
using namespace std;

int main() {
    int n = 65536;

    int bad = 0;                      // 32 位累加器
    for (int i = 1; i <= n; ++i) bad += i;
    cout << bad << "\n";            // -2147450880，溢出后的残值

    long long good = 0;               // 64 位累加器，同一个循环
    for (int i = 1; i <= n; ++i) good += i;
    cout << good << "\n";           // 2147516416

    int a = 100000, b = 100000;
    cout << a * b << "\n";         // 1410065408，先按 32 位乘完
    cout << 1LL * a * b << "\n";     // 10000000000，1LL 把式子抬到 64 位
    return 0;
}

第一行是 -2147450880，第二行是 2147516416。同一个循环、同一个 n，差别只在声明那一行——而编译器一句警告都没有。

4两条边界：溢出是静默的、看中间量不看结果

溢出最麻烦的地方不是结果错，而是它错得毫无提示：

验证 / 关键

溢出是「静默」的：编译器不警告、程序不崩溃、样例照样对，只有大数据会输出一个荒唐的数字。所以类型选择不能靠运行结果来试，必须在写代码前用乘法估一遍。

估的时候别只看答案：long long ans = a * b 里答案本身是 10¹⁰，long long 完全装得下，但乘法那一步是在 32 位里做的。看中间量，不看结果。

于是我们得到：写累加器之前先用「项数 × 单项最大值」估一遍上界：超过 2.1×10⁹ 就用 long long，拿不准也先用。溢出不报警、不崩溃、样例照样对，所以类型必须在写代码时定对，不能靠运行结果试。

三张卡拼起来，就是例题的全部零件：for 让 i 从 1 走到 n，sum += i 把这 n 项收进同一个变量，long long 保证这个变量装得下 5×10¹³。下一张图把它们连成一条执行路线。

判断方框在圈的开头，这一点值得多看两眼：i 先被问一次「你还在 1..n 里面吗」，通过了才把 i 加进 sum。所以 i = n 的那一圈确实被加进去了，答案才是 n 项而不是 n−1 项——循环题里绝大部分的差一错误，都能在这张图上找到位置。

提交前先用三组自测

n = 1 → 1；n = 100 → 5050；n = 10⁷ → 50000005000000。

第三组能过，说明 long long 选对了；如果输出的是 -2004260032 这种负数，说明 64 位没落实——多半是 sum 还写着 int。

这一节最容易犯的 4 个错（附症状）

WA · 累加器不初始化。写成 long long sum; 然后直接 sum += i，局部变量的初值是栈上残留的旧数据，同一份代码跑两次结果都可能不同；样例小的时候容易碰巧对上，一交大数据就挂。

WA · 边界差一次。i < n 只有 n−1 轮，最后一项被关在循环外面；i <= n 写成 i <= n + 1 则多算一项。拿 n = 1 试一次，正确答案是 1，输出 0 就是少了一轮。

WA · 用 int 求和。int sum = 0 一路加到 65536 得到 -2147450880，一个负数。它不报错、不崩溃、样例照样过（n = 100 的和才 5050），只有大数据露馅，是最难靠样例发现的一类。

WA · 乘法先溢出再赋值。long long ans = a * b; 里 a、b 都是 int，乘法先按 32 位算完，残值再存进 64 位变量；(long long)(a * b) 错得一模一样。只有 1LL * a * b 或者把 a 本身声明成 long long 才对。

自己动手复现

数学补给 · n(n+1)/2 与「先乘后除」的危险

把 1 到 n 正着写一遍，再倒着写一遍，上下对齐：第一列 1 与 n、第二列 2 与 n−1、最后一列 n 与 1，每一列的和都是 n+1，一共 n 列。所以 2S = n(n+1)，S = n(n+1)/2。高斯当年的做法，也是本类题最好的验算工具。

公式最大的价值是「写代码之前就能算」。拿它代一下最坏情况：n = 10⁷ 时 S = 5.0000005×10¹³，比 int 的上限 2147483647 大两万倍，所以累加器必须是 64 位。这一步只花十秒，却能省掉一次 WA 和半小时的排查。

它还能精确算出 int 哪天不够用。解 n(n+1)/2 > 2147483647，得 n ≥ 65536：65535 的和是 2147450880，离上限只差 32767；65536 的和是 2147516416，刚好越线，回绕成 -2147450880。本节反复出现的这两个数，就是从这里来的。

n1+2+…+n用什么类型装

公式自己也会溢出，而且危险在中间：n(n+1) 比最终结果大一倍，先乘后除的顺序改不掉。n = 10⁹ 时中间量约 10¹⁸，n 如果还是 int，乘的那一瞬间就已经错了；n 是 long long 时安全区一直到 n ≈ 3.03×10⁹（此时 n(n+1) ≈ 9.2×10¹⁸，逼近 2⁶³−1），再往上连 long long 都装不下中间量，只能先除后乘、或者换更宽的表示。

所以「用公式」不等于「不会溢出」。换公式只是把循环次数从十亿降到零，类型仍然要按中间量重新估一遍——这两件事在竞赛里从来是分开算的。

  2. 把累加器写成 int sum，n 从 1 开始慢慢增大，第一个开始出错的 n 是多少？出错时程序会崩溃吗？

    不会崩溃，也不会报错：高位被丢掉，低位照常显示，程序安静地输出一个负数。这就是溢出最危险的地方——它不给你任何提示。
    常见错路：①以为 int 上限是「21 亿个数」所以 n 到 10⁹ 才出事，其实 n = 10⁵ 时和已经 5×10⁹；②以为溢出会让程序段错误，于是去查数组越界。
  3. a、b 都是 int，各等于 100000。long long ans = a * b; 为什么错？1LL * a * b、(long long)a * b、(long long)(a * b) 三种改法哪些对？
    想好了？点开核对思路与解析
    结论：第一种写法输出 1410065408，第二种写法输出 10000000000。
    理由：表达式的类型在「计算的那一刻」由操作数决定，和左边拿什么变量接收毫无关系。a * b 两边都是 int，就先按 32 位乘出一个残值，再把这个残值转成 64 位存起来。
    三种改法里，1LL * a * b 和 (long long)a * b 都对：乘法从左往右算，第一个乘数变成 64 位后，整条式子就都是 64 位了。(long long)(a * b) 错，括号里的乘法早就按 32 位算完了，转换只是把残值搬个地方。
    常见错路：用 double 中转。10¹⁰ 时它碰巧还准，数据一到 10¹⁸ 就开始丢末尾几位。
  4. 本题 n ≤ 10⁷ 用循环没问题。如果 n 的上限改成 10⁹，循环还能用吗？换成公式之后，最危险的一步在哪？
    想好了？点开核对思路与解析
    结论：10⁹ 次循环在评测机上要好几秒，稳 TLE，必须换公式；换公式后最危险的一步是 n * (n + 1) 这个乘法，n = 10⁹ 时中间量约 10¹⁸，n 若是 int 就先在 32 位里溢出了。
    理由：中间量比最终结果大一倍，而「先乘后除」的顺序没得选——先把 n 除 2 只在 n 是偶数时成立，奇数时会丢半个 n。
    正确写法：n 声明成 long long（或者写 1LL * n * (n + 1) / 2），让乘法一开始就在 64 位里做。
    常见错路：①(long long)(n * (n + 1)) / 2，括号里已经溢出了；②n / 2 * (n + 1) 以为先除能避险，n 是奇数时答案少一半。

挑战题 · 阶乘之和
同类题 · 洛谷 P1009（弱化版）入门去洛谷做这题 ↗

给定一个正整数 n，求 1! + 2! + … + n! 的值。例如 n = 3 时，答案是 1 + 2 + 6 = 9。

输入格式：一行一个整数 n（1 ≤ n ≤ 20）。输出格式：一行一个整数，表示这个和。

数据范围刻意只到 20：20! = 2432902008176640000，连同前面的项加起来是 2561327494111820313，还在 long long 的上限 9.22×10¹⁸ 之内；n = 21 时只这一项就有 5.1×10¹⁹，立刻越界。

样例
输入： 3 输出： 9
引导性提示（先只看这里）

每一轮都要从 1 重新乘到 i 去算 i! 吗？上一轮算出来的乘积，离 i! 只差一个因子。

需要两个变量：一个滚动的阶乘（初值 1），一个收集答案的和（初值 0）。注意两句的先后。

答案有 19 位，两个变量都得能装下 19 位的数。int 在 n = 13 那一轮就已经翻了。

先手算 n = 1、2、3：答案分别是 1、3、9。程序对上了再提交。

想看思路了？点开完整思路

先看暴力：外层枚举 i，内层从 1 乘到 i 得到 i!，再累加。n = 20 时是 20 轮、每轮最多 20 次乘法，一共 400 次运算，能过，但其中 19 轮的工作是重复的。

改成递推：i! = (i−1)! × i。一个变量 fact 从头滚到尾，每轮只乘一次，总运算量降到 20 次乘法，这就是把「重算」换成「接着算」。

顺序是关键：必须先把 fact 更新成 i!，再加进 sum。反过来的话，sum 里加的是 (i−1)!，n = 3 时输出 3 而不是 9，而且样例小的时候特别容易蒙对别的东西。

边界：n = 1 时循环正好跑一轮，fact = 1、sum = 1；fact 的初值写 0 会让每一项都变成 0，写 2 会让 1! 那项变成 2。

数值：Σk=1..20 k! = 2561327494111820313，19 位，long long 上限 9223372036854775807 装得下。这也是题目把 n 卡在 20 的原因——再大就必须上高精度了。

复杂度：O(n) 时间、O(1) 空间，n = 20 时 20 次乘法加 20 次加法。

还是不会？点开题解代码与拆解
参考代码
#include <bits/stdc++.h>
using namespace std;

int main() {
    int n;
    cin >> n;                       // 1 <= n <= 20

    long long fact = 1;             // 求积的初值必须是 1
    long long sum = 0;              // 求和的初值是 0
    for (int i = 1; i <= n; ++i) {
        fact *= i;                  // (i-1)! 乘上 i 就是 i!，只乘一次
        sum += fact;                // 把第 i 项加进答案
    }

    cout << sum << "\n";
    return 0;
}
关键片段拆解
片段作用
long long fact = 1;滚动阶乘。初值 1 是乘法的单位元，第一次 fact *= 1 不改变结果；写 0 则所有项恒为 0。
long long sum = 0;求和累加器。和 fact 一样必须 64 位，13! 就已经超过 int 上限。
fact *= i;把上一轮的 (i−1)! 变成 i!。这一句让内层循环彻底消失，总复杂度从 O(n²) 降到 O(n)。
sum += fact;先乘后加。两句一换顺序，sum 里加的就成了 (i−1)!，n = 1 时直接输出 0。
for (int i = 1; i <= n; ++i)n ≤ 20，最多 20 轮，一轮不多一轮不少。
cout << sum循环结束后只输出一次，不要写在循环体里。
这题最容易错的地方
  • 把 sum += fact 写在 fact *= i 前面：加进去的是上一项，n = 3 时输出 3，n = 1 时输出 0。
  • 两个变量有一个写成 int：n = 13 时 fact = 6227020800 越界，输出一个随机负数，而样例 n = 3 完全正常。
  • 每轮重算阶乘（内层再写一个 1..i 的循环）：本题数据小，能过，但换个 n = 10⁵ 的版本就白写了一遍。
  • 把输出写进循环体：会打印 n 行中间结果，答案格式全错。
